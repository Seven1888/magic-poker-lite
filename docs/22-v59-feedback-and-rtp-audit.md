現行模型是 `pooled-holdem-v1 + two-boss-price-response-v4`。匹配底池全額派彩，`targetRtp = 1`；`.99` 用於 root 與玩家付費轉贏的計分。既有規格已提醒「計分設定不等於實測 RTP」，但這個提醒本身不能證明模型符合預期返還，也不能代替對數學錯誤的修正。

## 3. 已確認的四個結構性問題

### 3.1 win 永久繼承，又不斷增加轉贏機會

root 依匹配盲注計分，正常 `.99` 會得到 `49.5%` win。之後已 win 的路徑永久繼承；尚為 nonWin 的路徑，每次玩家付費又可轉 win。付費後底池變大，原 win 路徑的返還金額同步增加，卻沒有重新核算這項增加的返還責任。

在空池、排除棄牌與平手的診斷條件下，設付費前整體 win 機率為 `q`、玩家原投入為 `C`、本次付款為 `c`：

```text
q' = q + (1 - q) × [α × c / (2 × (C + c))]
```

從 `q = α / 2 = 0.495` 開始，只要 `c > 0`，`q'` 就會大於 `0.495`。若終局匹配底池全額派彩，這已否定「設定 α=.99 就能控制整體 RTP 為99%」的說法。後續棄牌或行為權重可能改變觀測結果，但不能補上缺失的數學約束。

程式依據：[root 報價](../src/outcome-pools.mjs#L163)、[付費報價](../src/outcome-pools.mjs#L218)、[win 繼承與轉換](../src/outcome-pools.mjs#L260)。

### 3.2 同一筆成功轉贏付款，同時買勝率與產生池信用

現行程式在付款後 `target === 'win'` 時就新增延後入池信用。這包含「原本 nonWin，本次抽票成功轉 win」，不只是付款前已經 win 的路徑。因此本次 `.99 × 付款` 已用於轉贏概率，又在成功分支產生另一筆可供後續轉贏使用的水池信用。

這是現行契約明確實作的行為，既有測試也將它列為正確結果；問題在於沒有建立能證明同筆預算未被重複使用的整體期望返還模型。只檢查池末等於池初減使用加信用，不會發現這個缺口。

程式依據：[成功後新增信用](../src/outcome-pools.mjs#L268)、[終局按有效付款入池](../src/outcome-pools.mjs#L335)。

### 3.3 nonWin 包含平手，報價卻沒有平手返還項

建牌器把玩家未嚴格獲勝的結果都歸入 nonWin，其中包含平手。結算時平手會返還一半匹配底池，然而 root／付費轉贏報價只以 win 的完整底池返還建立概率，沒有單獨核算 nonWin 中的平手返還。

真引擎 seed `28` 的診斷例：SB1／BB2，玩家先 CALL1，之後雙方選合法 CHECK／CALL；root 是 nonWin，付費抽票也沒有轉 win，最後仍平手。玩家有效投入 `2`、返還 `2`、本手入池 `0`。因此 nonWin 絕不能當成零返還。

程式依據：[win／nonWin 分類](../src/outcome-layout.mjs#L25)、[平手派彩](../src/engine.mjs#L402)。完整牌面與行動紀錄見 分支診斷 JSON（本機證據：`output/math-audit-v59-contract.json`）。

### 3.4 FOLD 改變終局返還，池使用仍依假設完整跟注的底池

付費報價的分母先假設玩家新增投入可以被 NPC 匹配。若之後 NPC FOLD，實際匹配底池可能小得多；程式會退還未匹配籌碼，也會裁切入池信用，卻不以實際終局重新核算已消耗的轉贏預算。另一方面，NPC FOLD 可讓 nonWin 路徑直接獲勝；玩家 FOLD 也可讓 win 路徑直接落敗。這些行為分支並未納入單一返還預算。

具體例：SB1／BB2、初始付費池 `1000`、root nonWin、玩家 ALL IN99。

| 項目 | 現行結果 |
| --- | ---: |
| 付費報價匹配底池分母 | 200 |
| 本次付款計分 | 98.01 |
| 消耗付費池 U | 101.99 |
| 轉 win 機率 | 100% |
| NPC FOLD 後玩家有效投入 | 2 |
| 玩家實際返還 | 4 |
| 未匹配退款 | 98 |
| 有效付款入池信用 | 0.99 |
| 終局付費池 | 899 |

`1000 - 101.99 + 0.99 = 899` 的池帳完全一致，但不能因此說 `101.99` 的預算已轉成相應期望返還。報價假設的底池與實際終局底池不同，這必須在新模型中明確處理。

程式依據：[假設可匹配金額與池使用](../src/outcome-pools.mjs#L224)、[FOLD 決定勝負](../src/engine.mjs#L381)、[只裁切入池信用](../src/outcome-pools.mjs#L335)。

## 4. 精確 CALL 與 ALL IN 反例

以下是隔離機制診斷：空池、`.99` 計分、SB1／BB2、玩家起始100；NPC 選擇合法 CHECK／CALL 到攤牌，計算先排除平手。**這不是正式 BOSS 策略的長期 RTP，也不是新的建議機率表。**

### 玩家 CALL1

```text
root win                         = 0.495
root nonWin                      = 0.505
nonWin 本次轉 win 機率            = 0.99 / 4 = 0.2475
最終 win 機率                    = 0.495 + 0.505 × 0.2475
                                 = 0.6199875
期望返還                         = 4 × 0.6199875 = 2.47995
有效投入                         = 2
返還／投入                       = 123.9975%
另產生的期望付費池信用            = 0.99 × 0.6199875
                                 = 0.613787625
```

三個精確分支為：root win 繼承 `49.5%`、nonWin 成功轉 win `12.49875%`、nonWin 轉換失敗 `38.00125%`。兩種 win 分支均返還4且入池0.99；失敗分支在無平手假設下返還0且不入池。

真引擎亦找到三個可重現實例：seed `0` 為 root win、seed `5` 為付款後轉 win、seed `8` 為轉換失敗。完整牌面、行動及結算保存在診斷 JSON。seed28 的平手例說明實際 nonWin 還存在額外返還，不能把上述簡化診斷當作完整正式策略研究。

### 玩家 ALL IN99，NPC 跟注

```text
nonWin 本次轉 win 機率 = 98.01 / 200 = 0.49005
最終 win 機率         = 0.495 + 0.505 × 0.49005 = 0.74247525
有效投入             = 100
返還／投入           = (200 × 0.74247525) / 100
                     = 148.49505%
```

上述反例不使用水池，因此即使改 CD 或初始池金額，也無法消除 win 繼承及後續轉贏帶來的結構問題。

## 5. 現行正式規則的四策略有限樣本

本批每個策略都是32名獨立玩家、每名64手，共2048手；四組合計8192手。固定研究 seed `590701`，SB1／BB2，每桌起始買入100；初始三桶一般池與特殊池均為0，CD上下限0；使用 `continuous` 模式與無限外部研究錢包。

「無限外部錢包」僅允許桌碼歸零後重新買入，不代表每手補滿。桌碼在同桌跨手真實延續，重新入桌另記 `tableEntries`／`tableBuyIns`。現行正式 BOSS 行為仍使用原本規則。玩家策略也是既有 CALL／平衡／積極／保守策略；它們沒有讀取隱藏結果目標、未揭公牌或 NPC 暗牌。CALL 策略選合法 CALL／CHECK，其餘三種依玩家自己的底牌、已揭公牌與價格選動作，並非知道結果的 oracle。

RTP 分母是實際有效匹配投入；分子是玩家真正收到的 `totalReturns`。未匹配退款、買入、初始水池或未派水池餘額均未當作 RTP 返還。

## 6. 原有測試為何沒有擋住

既有測試能驗證本次選項與預覽相同、公式照指定值運行、籌碼守恆、退款正確、水池不透支、存檔冪等與重整結算等功能。這些檢查仍有價值，但範圍不足以證明整體返還正確。

- [引擎守恆檢查](../tests/pooled-holdem-engine.test.mjs#L29) 檢查雙方籌碼總和，以及池末等於池初減使用加信用；沒有檢查「期望返還＋剩餘返還預算」的整體關係。
- [成功轉贏再入池測試](../tests/outcome-pools.test.mjs#L92) 與 [win 繼承再入池測試](../tests/outcome-pools.test.mjs#L119) 將現行設計本身列為預期值；公式若存在設計問題，照公式通過也不會發現。
- 先前的少量遊戲與工具驗收主要證明流程可用。小樣本不能證明長期 RTP，測試全部通過也不能替代數學證明。

後續需要加入能反駁錯誤公式的期望值、分支及預算測試，不能只把現行實作結果再抄為測試答案。

## 7. 數學重建方向與未完成工作

下一版應先建立**單一期望返還預算**，明確定義每筆有效投入能增加多少預算、何時消耗、何時保留，以及未匹配退款如何沖回；同一筆金額不能同時購買當前轉贏機會，又無成本增加未來可派預算。

必須重新評估 win 繼承、nonWin 轉換、平手與雙方 FOLD／CALL／RAISE 分支。預算要對應分支真正的返還與有效匹配投入，不能只看按鈕倍率或假設對手一定完整跟注的底池。BOSS 行為概率與其根據牌面變化的分類要納入評估，而非事後以任意提高 FOLD 壓低研究數字。

後續先對小型可列舉分支證明期望返還與預算關係，再做多策略、多種子、跨玩家的研究；同時保留籌碼、池、退款、短全下、盲位及存檔檢查。不同玩家策略可改變實際回報，應明確定義目標適用的策略與統計口徑，不能承諾任意玩家行為都固定99%。

這份文件沒有核准任何新概率、未選定替代模型，也沒有修改現行正式數學。若後續更換決策或返還模型，舊未完桌須按保存的舊契約完成，再遷移到新版；不能直接替換全域公式而改掉舊桌尚未結清的結果。

數學待辦為：完成方案與參數依據、實作正式模型修正並驗證。四項非數學修正可獨立發布為 v59；在數學驗證完成前，不寫「RTP 已修正」。

## 9. 修正方向的小型求解驗證（2026-10-07）

使用者追問「知道該怎麼調整嗎」。本輪先把修正方向變成可重現的小型求解器，尚未替換正式引擎，也未決定新版 BOSS 百分比。

### 單一預算與可達範圍

- 用 `min(雙方累計投入)` 的實際匹配增量建立計分預算。玩家先推入但尚未被匹配的金額保持待確認，不先創造可花預算；最終未匹配退款也不列有效投入。
- 取消永久 win 旗標作為派彩承諾。每個狀態記錄已配置的返還期望價值，新增付款只能增加相應預算，不能同時再記一筆成功轉贏入池信用。
- 對每個合法玩家動作，聯合求解 BOSS 行動、實際輸／平／贏與後續狀態的機率。公開預覽與正式抽樣須使用同一份解，不能各自調表。
- 終局小樹先核對 `E[實際返還 + 期末池] = 期初池 + .99 × E[有效投入]`。完整多步模型還須納入未結束狀態的返還期望價值；這個等式本身不代表所有玩家策略的實現 RTP 都恰好99%。
- 先算每個候選集合能達到的最低／最高返還。預算落在區間外就回報不可行，不能截斷負機率或超過100%的機率後宣稱已校準。

### 已通過的精確終局例

腳本 rtp-repair-v59-terminal.mjs（本機證據：`output/rtp-repair-v59-terminal.mjs`） 枚舉一個 FOLD／CALL 後直接終局的小樹，結果見 JSON（本機證據：`output/rtp-repair-v59-terminal.json`）。表中70%、2%等是診斷條件，**不是新的正式建議概率**。CALL 後直接終局的假設不代表正常2×／4×加注後不能再加注。

| 診斷條件 | 求得 CALL 後 win 機率 | 結果 |
| --- | ---: | --- |
| 對手全CALL／CHECK，投入2、底池4、無平手／空池 | 49.5% | 期望返還1.98，比例99% |
| POT3、玩家實付6，BOSS FOLD70%、CALL30%、無平手／空池 | 15.833333% | 有效投入期望3.5，返還3.465，比例99% |
| POT3、玩家實付12，BOSS FOLD70%、CALL30%、無平手／空池 | 31.371795% | 有效投入期望5.3，返還5.247，比例99% |
| 玩家ALL IN99，BOSS FOLD70%、CALL30%、無平手／空池 | 47.143333% | 有效投入期望31.4，返還31.086，比例99% |
| 上例CALL分支另有2%平手 | 46.143333% | 平手返還也納入後，比例99% |

另驗證期初池20、只有CALL分支使用10、CALL分支有2%平手的例子：期望期末池17，期望返還34.086，兩者總和51.086恰等於20加`.99×31.4`。本期實現返還比例高於99%是使用既有預算的結果；剩餘池仍不是玩家本期返還。這只是單樹的期望守恆，不是跨手穩態證明。

### 已確認不能硬調的情況

- POT3、玩家實付6，若BOSS FOLD80%，光棄牌已貢獻返還期望3.2，大於`.99×有效投入期望3 = 2.97`。即使CALL後永遠讓玩家輸，也無法在此小樹達標。
- 同樣實付6、FOLD70%，若候選只有「win或tie」而不能嚴格輸，最低返還已4.9，超過預算3.465。求解器必須拒絕，不能把nonWin當0返還。
- 皇家等自然不可輸牌仍須保留。不能為了每手都有嚴格輸的候選而剔除這類牌；完整模型須在上游牌面分布與跨手預算一起分配成本，允許個別手高於目標。

### 正式整合前還需完成

將單樹擴展到多次加注、四街、短全下、玩家根據已揭牌與公開機率調整行動的情境；逐個資訊狀態與合法動作檢查可達範圍，不能用對玩家不可見的狀態混平均掩蓋可利用的優勢。還要明確指定RTP驗收的策略口徑，並檢查期末未派池相對總投入是否有界、是否收斂。

目前已驗證修正機制的局部算例與不可行檢測，**尚未證明完整遊戲已達99%，也尚未把這些概率寫入遊戲**。舊桌仍須保存原契約完成，新的數學模型應有獨立版本以免重整或遷移改掉舊桌帳務。

另有 多步預算原型（本機證據：`output/rtp-repair-v59-budget-tree.mjs`） 與 輸出（本機證據：`output/rtp-repair-v59-budget-tree.json`），枚舉8種診斷策略，包括2×／4×／ALL IN、面對再加注後CALL／FOLD／再ALL IN，以及依公開訊號改選動作。各觀測狀態與玩家動作檢查：

```text
E[即時返還 + 下一狀態池 + 下一狀態已配置價值 - .99×新增有效匹配投入]
    = 目前池 + 目前已配置價值
```

8種策略的期望預算殘差最多約`1.8e-15`。原型刻意保留一部分未派價值到池中，因此實際返還比例不等於99%，也再次驗證「池未派出不能算RTP」。這個小樹沒有真實牌面頻率、完整四街或全部玩家策略，不能代替正式模型與長期驗收；其中的機率與預留比例都不是新遊戲設定。
